# AI tool reference

Technical reference for the 37 tools the AI side panel's model can call. For
the "why" behind the architecture (dispatch pipeline, confirmation
conventions, prompt design), see [`ai-panel-handover.md`](ai-panel-handover.md)
and [`tickets.md`](tickets.md). This doc is the "what" — exact input/output
shapes — generated by reading `backend/ai_tools/{schemas,specs,tools}.py`
directly; regenerate/re-verify against that source if it drifts.

## How dispatch works

Every tool call — whether issued by the model during `POST /api/v1/ai/chat`
or invoked directly via `POST /api/v1/ai/tools/{tool_name}` — goes through
`dispatch_tool_call(db, tool_name, arguments)` (`backend/ai_tools/dispatch.py`):

1. **Schema validation** — `arguments` is parsed against the tool's Pydantic
   argument model (`TOOL_ARG_MODELS`, `backend/ai_tools/schemas.py`). Unknown
   fields are rejected (`extra="forbid"` on every model). Failure returns
   `{"success": false, "reason": "<field>: <message>; ..."}`.
2. **Business validation** — not reimplemented here; each executor calls
   straight into the same route-handler function the human-driven HTTP API
   uses, so template-exists/event-exists/etc. checks can't drift between the
   two paths.
3. **Permission validation** — currently a no-op pass-through (no auth system
   exists in this admin backend by design).
4. **Execution** — the executor runs and returns a plain `dict`. Any
   `ToolValidationError` or `HTTPException` raised along the way, or any
   other unexpected exception, becomes `{"success": false, "reason": "..."}"`
   instead of propagating.

**Every call returns one of two shapes:**

```jsonc
// success
{"success": true, "result": { /* tool-specific, see below */ }}
// failure (schema rejection, business-rule violation, or unexpected error)
{"success": false, "reason": "human-readable explanation"}
```

Every call — success or failure — also writes one row to `ai_audit_log`
(`tool_name`, `arguments`, `success`, `entity_id`, `reason`).

**List-shaped results** generally use the envelope
`{"items": [...], "total": int, "limit": int, "offset": int}` (from
`list_envelope`); a few (roles, signups-across-events variants, some TICKET-54
tools that don't paginate) return just `{"items": [...]}` — noted per tool
below. `limit`/`offset` args default to 50/0 and cap at 100 unless stated
otherwise.

**Mutating/irreversible tools require a preview step first**, enforced only
by `SYSTEM_PROMPT` convention (no code-level gate — see `tickets.md`
TICKET-49, dropped by design): `create_event_draft` → `publish_event`,
`preview_announcement` → `send_announcement`, `preview_shift_reminder` →
`send_shift_reminder`, `preview_certificate_generation` →
`generate_event_certificates`. `approve_event_signup` and `cancel_event` have
no preview step but `SYSTEM_PROMPT` instructs the model to only call them
after explicit organizer confirmation.

## Events

### `create_event_draft`
Validates a proposed event (template exists, defaults resolve) and returns
it as a draft. **No database write.**
- **Input:** `event_template_id` (int|null, required), `name` (str, required),
  `venue` (str, required), `event_date` (date, required), `description`
  (str|null), `start_time`/`end_time` (time|null), `beneficiary_id` (int|null),
  `expected_attendance` (int≥0|null).
- **Output:** `{"status": "draft", "event": {...same fields as input, resolved...}}`.

### `publish_event`
Creates a real event from an approved draft. Same input shape as
`create_event_draft`.
- **Output:** `EventDetail` — `id, name, venue, event_date, description,
  start_time, end_time, status, beneficiary_id, expected_attendance,
  is_cancelled, event_time, event_template_id, created_at, updated_at, tasks: []`.

### `update_event`
Partial update of an existing event.
- **Input:** `event_id` (int, required) + any subset of `name, venue,
  event_date, description, start_time, end_time, status, beneficiary_id,
  expected_attendance`.
- **Output:** `EventDetail` (see above).

### `get_event`
- **Input:** `event_id` (int, required).
- **Output:** `EventDetail`, including `tasks: EventTaskOut[]` (`id,
  team_member_id, template_task_id, name, body, due_at, category, status,
  position, subtasks: EventSubtaskOut[]`).

### `list_events`
- **Input (all optional):** `status`, `date_from`, `date_to`, `template_id`,
  `beneficiary_id`, `q`, `limit`, `offset`.
- **Output:** envelope of `EventDetail`-shaped items (without `tasks`, per
  `EventSummary`).

### `cancel_event`
Sets `is_cancelled` and closes registration — distinct from the `status`
open/closed toggle. Never hard-deletes.
- **Input:** `event_id` (int, required).
- **Output:** `EventDetail`.

### `list_event_templates`
- **Input (all optional):** `is_built_in` (bool), `q`, `limit`, `offset`.
- **Output:** envelope of `TemplateOut` — `id, name, description,
  is_built_in, beneficiary_id, created_at, updated_at`.

## Tasks

### `list_event_tasks`
- **Input:** `event_id` (int, required); optional `category`
  (`TaskCategory`), `status` (`TaskStatus`), `team_member_id`, `due_before`,
  `due_after` (dates), `limit`, `offset`.
- **Output:** envelope of `EventTaskOut` (see `get_event` above).

### `assign_event_task`
Assigns a task to a team member, or unassigns with `team_member_id: null`.
Never targets a volunteer.
- **Input:** `event_id`, `task_id` (both int, required), `team_member_id`
  (int|null, required — must be passed explicitly, no default).
- **Output:** `EventTaskOut`.

### `update_task_status`
One tool over three status-transition handlers (start/complete/reopen).
- **Input:** `event_id`, `task_id` (int, required), `status`
  (`"ongoing"|"done"|"incomplete"`, required).
- **Output:** `EventTaskOut`.

### `list_upcoming_deadlines`
Cross-event: tasks due soon, not scoped to one event.
- **Input (all optional):** `days` (1–365, default 14), `team_member_id`,
  `limit` (1–100, default 20).
- **Output:** `{"items": [{id, event_id, event_name, name, due_at, category,
  status, team_member_id}], "total": int}`.

## Volunteers

### `list_volunteers`
- **Input (all optional):** `signup_status`, `skill_id`, `role_id`, `q`,
  `limit`, `offset`.
- **Output:** envelope of `VolunteerListItem` — `id, name, contact_number,
  email, signup_status, skills: string[], counts: {events_signed_up,
  events_approved, events_attended}`.

### `list_event_roles`
- **Input:** `event_id` (int, required).
- **Output:** `{"items": [RoleOut]}` — `id, name, category, is_required`.
  **No pagination envelope** (unlike most list tools).

### `list_event_signups`
- **Input:** `event_id` (int, required); optional `status`, `role_id`,
  `attendance` (bool), `q`, `limit`, `offset`.
- **Output:** envelope of `SignupOut` — `id, event_id, volunteer_id,
  volunteer_name, status, assigned_role_id, assigned_role_name, is_leader,
  attendance`.

### `list_pending_signups`
Cross-event version of `list_event_signups` (same filters, minus `event_id`)
— for phrasings that name no specific event.
- **Input (all optional):** `status`, `role_id`, `attendance`, `q`, `limit`,
  `offset`.
- **Output:** envelope of `{id, event_id, event_name, event_date,
  volunteer_id, volunteer_name, status, assigned_role_id,
  assigned_role_name, is_leader, attendance}` — same fields as `SignupOut`
  plus `event_name`/`event_date` since results span every event.

### `approve_event_signup`
Only reached after the organizer explicitly confirms a specific
recommendation — never auto-approved by the model.
- **Input:** `event_id`, `signup_id` (int, required), `assigned_role_id`
  (int, required), `is_leader` (bool, default false).
- **Output:** `SignupOut`.

## Inventory (read-only — writes deliberately out of scope, no organizer use case identified yet)

### `list_inventory_items`
- **Input (optional):** `limit`, `offset`.
- **Output:** envelope of item rows with `is_active` coerced to bool (id,
  name, sku, item_type, unit, reorder_level, is_active, ...).

### `list_inventory_locations`
- **Input (optional):** `limit`, `offset`.
- **Output:** envelope of location rows (`is_temporary`/`is_active` as bool).

### `get_stock_levels`
No filters — mirrors the unfiltered `GET /inventory/stock`.
- **Input:** none.
- **Output:** `{"items": [{item_id, item_name, sku, item_type, unit,
  reorder_level, location_id, location_name, on_hand, reserved, available,
  expiring, reorder_status: bool}], "total": int}`.

### `list_inventory_movements`
- **Input (optional):** `limit`, `offset`.
- **Output:** envelope of stock-movement rows joined with item/location
  names.

## Broadcast (WhatsApp) — preview/send pairs, sends are irreversible

### `preview_announcement`
No DB write.
- **Input:** `event_id` (int, required), `title` (str, min 1), `body` (str,
  min 1), `audience` (`"all"|"participants"|"volunteers"`, default `"all"`).
- **Output:** `{"event_id", "title", "body", "audience", "recipient_count"}`.

### `send_announcement`
**Sends real WhatsApp messages — only call after the organizer confirms the
matching preview.** Same input shape as `preview_announcement`.
- **Output:** `AnnouncementOut` — `id, event_id, title, body, audience,
  kind: "announcement", created_by_team_member_id, created_at, sent_at,
  delivered_count, failed_count`.

### `preview_shift_reminder`
No DB write. Always targets the `"volunteers"` audience.
- **Input:** `event_id` (int, required), `body` (str|null — auto-generated
  default reminder text if omitted).
- **Output:** `{"event_id", "body", "audience": "volunteers",
  "recipient_count"}`.

### `send_shift_reminder`
**Sends real WhatsApp messages.** Input: `event_id`, `body` (str|null).
- **Output:** `AnnouncementOut` with `kind: "reminder"`.

## Reports and certificates

### `list_completed_event_reports`
Closed events only. **Redacts real names by default** — see `tickets.md`
TICKET-50.
- **Input:** `include_names` (bool, default `false` — set true only when the
  organizer's question needs the actual name list, not for headcount
  questions).
- **Output:** `{"items": [{id, name, date, venue, template_name,
  is_skills_workshop, report_status: "Complete"|"Incomplete", attendees: int,
  volunteers: int, partners: string[], generated_caption,
  participant_names?, volunteer_names?}]}`. `participant_names`/
  `volunteer_names` are present only when `include_names: true`. **No
  pagination envelope.**

### `list_event_certificates`
Certificates already issued for an event. **Never includes `download_token`
or `link`** — both are bearer-style access secrets, dropped unconditionally
(TICKET-50).
- **Input:** `event_id` (int, required).
- **Output:** `{"items": [{id, event_id, participant_id, volunteer_id,
  issued_at, delivered_at}]}`.

### `preview_certificate_generation`
No DB write — counts eligible recipients and how many already have a
delivered certificate. Always call before `generate_event_certificates`.
- **Input:** `event_id` (int, required).
- **Output:** `{"event_id", "eligible_participants", "eligible_volunteers",
  "already_delivered", "pending_delivery"}`.

### `generate_event_certificates`
**Generates certificates for everyone with recorded attendance and messages
the links on WhatsApp — irreversible.** Only call after the organizer
confirms `preview_certificate_generation`.
- **Input:** `event_id` (int, required).
- **Output:** `{"items": [CertificateOut]}` — same certificate shape as
  `list_event_certificates` (also without `download_token`/`link`, per the
  executor's redaction).

## Participants (TICKET-54)

### `list_event_participants`
The participant/RSVP roster for one event — distinct from volunteers.
- **Input:** `event_id` (int, required); optional `rsvp_status` (bool),
  `attendance` (bool), `q`, `limit`, `offset`.
- **Output:** envelope of `ParticipationOut` — `participant_id, name,
  contact_number, email, rsvp_status, attendance`.

### `get_participant`
- **Input:** `participant_id` (int, required).
- **Output:** `ParticipantOut` — `id, name, contact_number, email,
  created_at, updated_at`.

### `list_participants`
Cross-event participant search (not scoped to one event) — use
`list_event_participants` instead when the organizer names a specific event.
- **Input (optional):** `q`, `limit`, `offset`.
- **Output:** envelope of `ParticipantOut`.

## Venues (TICKET-54, read-only)

### `list_venues`
- **Input (optional):** `limit`, `offset`.
- **Output:** envelope of venue objects — `id, name, address,
  managing_organization_id, managing_organization_name, notes, is_active,
  spaces: [{id, venue_id, name, pax_capacity, accessibility_information,
  is_active}], booking_count: int`.

### `get_venue`
- **Input:** `venue_id` (int, required).
- **Output:** same shape as one `list_venues` item, plus `bookings:
  [{...booking row, event_name, space_name}]` (all bookings for this venue,
  most recent first).

### `list_venue_bookings`
Venue-space bookings for one event.
- **Input:** `event_id` (int, required).
- **Output:** `{"items": [{id, event_id, venue_space_id, is_primary, status,
  start_at, end_at, cost_sgd_cents, contact_id, notes, space_name,
  pax_capacity, venue_id, venue_name, expected_attendance,
  capacity_warning: bool}], "total": int}`.

## Logistics (TICKET-54, read-only)

### `get_attendance_forecast`
Projects expected attendance from historical show-up rates at similar past
events (same template, falling back to same beneficiary group if fewer than
2 similar events by template). Use instead of the raw RSVP count.
- **Input:** `event_id` (int, required).
- **Output:** `{"registrations": int, "historical_show_up_rate": float|null,
  "similar_event_sample_size": int, "suggested_attendance": int|null,
  "calculation_basis": "same_event_template"|"same_beneficiary_group"|
  "insufficient_history"}`.

### `get_event_logistics`
Full operational picture for one event in a single call — the
highest-priority tool from TICKET-54's own framing ("how are we doing
operationally for Saturday's event").
- **Input:** `event_id` (int, required).
- **Output:** `{"event": {id, name, status, expected_attendance}, "forecast":
  <get_attendance_forecast's output shape>, "requirements":
  [<list_event_logistics_requirements item shape>], "venue_bookings":
  [<list_venue_bookings item shape>], "reconciliation": {event_id, status,
  completed_at, notes}, "warnings": [{type: "shortage"|"late_delivery"|
  "capacity"|"expiring_stock", message, requirement_id?, booking_id?}]}`.

### `list_event_logistics_requirements`
Goods/services logistics requirements for one event.
- **Input:** `event_id` (int, required).
- **Output:** `{"items": [{id, event_id, requirement_type: "goods"|
  "service", name, required_quantity, unit, needed_by, priority, notes,
  is_cancelled, allocations: [...], inventory_reserved, inventory_issued,
  supplier_ordered, supplier_on_site, on_site, still_to_source,
  not_yet_on_site, status: "uncovered"|"sourced"|"on_site"|"fulfilled"|
  "cancelled"}], "total": int}`.

## Deliberately out of scope

- **`organizations.py` / `beneficiaries.py`** — no AI tools. Both hold
  PII-adjacent data for a vulnerable population (beneficiary contact/group
  data; external-partner contacts and supplier-order/pricing history) with
  no redaction pattern worked out yet, the same category of concern
  TICKET-50 addressed for participant/volunteer names. See TICKET-54 in
  `tickets.md` for the full reasoning.
- **Write tools for inventory/venues/logistics** (adjustments, transfers,
  booking creation, donation-batch transitions, requirement
  reserve/issue/reconcile) — deferred pending a concrete organizer chat use
  case, same rationale as inventory's original TICKET-39.
- **`delete_event`** — the one hard-delete, cascading operation in this
  area. No tool wraps it, and `dispatch_tool_call` rejects the name outright
  if a model ever hallucinates it (`{"success": false, "reason": "Unknown
  tool 'delete_event'"}`).
